# 约束解码：正则怎么可能作用在一个神经网络上？

这篇文档回答一串很自然的疑问：

1. 它是**推理引擎里写的一套规则**吗？可是我面对不同用户，他们各有各的语法，

3. 你举的 JSON 例子，**为什么在"约束解码阶段"就能实现这种效果**？那是 Transformer 里的一个步骤吗？
   我好像没在模型里见过这个。

## 0. 三个纠正（这是全部困惑的来源）

| 你的疑问 | 纠正 |
| --- | --- |
| "是推理引擎里写的一套规则吗？" | **引擎只实现"机制"，不拥有"规则"**。规则是**每个请求带进来的数据**，和 `max_tokens` 一样 |
| "正则怎么能用数学实现？" | **模型的数学一点没变**。约束做的事是：`logits[不合法] = -inf`，然后**照常** argmax。正则不是"算"出来的，是**编译成状态机**的 |
| "这是 Transformer 里的步骤吗？" | **不是**。它在 Transformer **外面** —— 选 token 那一步（本仓库的 `argmax` 那一行） |

**一句话**：Transformer 只负责**给 152,000 个候选打分**；"从中选哪个"是引擎的事。
约束解码就是**在打分和选择之间，把不合法的候选的分数改成 -∞**。

## 1. 它在哪一层

```
┌───────────────────────────── Transformer（神经网络）─────────────────────────────┐
│  embedding → 24 × attention/MLP → final norm → lm_head                            │
│                                        ↓                                          │
│                              logits [151,936]      ← 只是"每个候选的分数"           │
└────────────────────────────────────────┬──────────────────────────────────────────┘
                                         │   ← 到这里为止，一点约束都没有
┌────────────────────────────────────────▼──────────────────────────────────────────┐
│  引擎（Python / C++，和神经网络无关）                                              │
│    ① grammar 状态机：当前状态允许哪些【字符】                                       │
│    ② 预计算的 token 掩码：这个状态允许哪些【token】                                 │
│    ③ logits[不合法] = -inf        ← ★ 约束只在这一次发生                            │
│    ④ argmax / sample             ← 之后的流程完全没变                              │
└────────────────────────────────────────────────────────────────────────────────────┘
```

所以它**不在** `model.forward()` 里面，而在**调用方**——也就是本仓库这一个函数：

```python
next_token_id = int(outputs.logits[:, -1, :].argmax(dim=-1).item())
#                                 ^^^^^^^^^^ 约束就是在这之前插一个 mask
```

## 2. 正则怎么变成约束：编译成状态机

**关键认识：正则不需要"用数学算"，它用编译原理算。**

正则 `\d{4}-\d{2}-\d{2}` 编译成状态机（就是**自动机**，和神经网络毫无关系）：

| 状态 | 含义 | 允许的字符 |
| --- | --- | --- |
| 0~3 | 已经读了 0~3 个数字 | 只允许 `0`~`9` |
| 4 | 4 个数字读完了 | **只允许 `-`** |
| 5~6 | 月份数字进行中 | 只允许 `0`~`9` |
| 7 | 月份读完 | **只允许 `-`** |
| 8~9 | 日期数字进行中 | 只允许 `0`~`9` |
| 10 | **接受态** | 必须停 |

**但这里有个 gap**：状态机说的是"允许哪些**字符**"，
而模型输出的是"**token** 的分数"。一个 token 可能是 `1889`（4 个字符），
也可能是 `-`，也可能是 `\n`。

所以引擎必须预计算一张表：**对每个状态，哪些 token 合法**。
规则是"**这个 token 的每个字符都能从当前状态合法走完**"。

实测（Qwen2 词表 151,646）：

| 状态 | 合法 token 数 | 占词表 |
| --- | --- | --- |
| 0~3（该数字） | **10** | 0.007% |
| **4（该 `-`）** | **1** | **0.001%** |
| 5~6（该数字） | 10 | 0.007% |
| 10（接受态） | 0 | — |

**这就是约束的"力量"所在**：某一步 151,646 个候选里只剩 **1 个**合法 ——
模型没有"选错"的余地。

> 真实实现（`outlines` / `xgrammar` / `llguidance`）会把上面那张表压成
> **位掩码**（152K bit ≈ 19 KB）并**按状态缓存**。否则每步重算会非常慢。
> 它们还要处理**字节级**的 UTF-8 边界（本仓库的 demo 简化成了字符级）。

### 2.5 把 gap 补上：**"mask 凭什么知道 JSON 合法？"**

这是最容易卡住的一点。答案是：**mask 不知道，也不需要知道 —— 它只是一次过滤。**
"合法性"的知识被**事先编译**进了那张表里。分三级看同一件事，就清楚了。

#### 级别 1：手写 `if/else` —— 约束的**全部本质**，零数学

目标：只允许模型输出 `"YES"` 或 `"NO"`。规则长这样：

```python
def allowed_chars(so_far):
    if   so_far == "":    return {"Y", "N"}
    elif so_far == "Y":   return {"E"}
    elif so_far == "YE":  return {"S"}
    elif so_far == "YES": return set()      # 结束
    elif so_far == "N":   return {"O"}
    elif so_far == "NO":  return set()      # 结束
    else:                 return None       # 非法前缀
```

生成时就这么用：

```python
allowed = allowed_chars(已生成的文本)
logits[所有不在 allowed 里的 token] = -inf     # ← mask 就是这么来的
next_token = argmax(logits)                    # ← 只能在 allowed 里选
```

**看：这里没有正则、没有数学、没有神经网络。就是普通的 `if/else`。**
所谓"约束"就是这份表 + 一次过滤。`argmax` 只能从非 `-inf` 的里选 ——
**如果某一步只剩 1 个非 `-inf`，`argmax` 就必须选它**（§3 实测的状态 4 就是这样）。

实测走一遍：

```
走 'YES'：      已生成 ''   → 允许 ['N','Y']
                已生成 'N'  → 允许 ['O']
                已生成 'NO' → 允许（结束）
走 'YEP'（非法）：已生成 'YE' → 允许 ['S']；输入 'P' → ❌ 被拒绝
```

#### 级别 2：正则只是"写规则的语法"，会被**编译**成级别 1 的表

手写级别 1 太累（JSON schema 会写出几千行 `if/else`），于是有了**正则**。
但正则**不是另一种数学** —— 它只是写规则的**方便语法**，
会被 **Thompson 构造**（1968 年的编译器算法，`grep`/`sed`/`awk` 用的就是它）
编译成"状态 → 允许字符"的表，也就是级别 1 那种东西。

| 正则 | 状态数 | 含义 |
| --- | --- | --- |
| `\d{4}-\d{2}-\d{2}` | 11 | 宽松：月份两位数字 |
| `\d{4}-(0[1-9]\|1[0-2])-\d{2}` | 12 | 严格：月份必须 01~12 |

> **状态必须"记得足够多"**：严格版里"`0` 之后"允许第二位是 1~9，
> "`1` 之后"允许 0~2 —— 两者不同，所以**必须是两个状态**（脚本里叫 `6a`/`6b`），
> 不能合并。这就是为什么严格 grammar 会多出状态。

用两个 grammar 验证**同一个输出 `1889-18-19`**：

| grammar | 结果 |
| --- | --- |
| 宽松 `\d{2}` | ✅ **接受** |
| 严格 `(0[1-9]\|1[0-2])` | ❌ **拒绝**（第 6 个字符 `8`，状态 `6b`） |

#### 🎯 这才是那个 gap 的答案

> **约束解码不检查"日期是否正确"。它只检查"是否符合你给的 grammar"。**
>
> "18 月是否合法"完全取决于**你写的 grammar 能不能表达 1~12**：
> 宽松 grammar 放行，严格 grammar 拒绝。
>
> **约束的能力上限 = 你用的形式语言能表达的东西**：
>
> | 能表达 | 不能表达 |
> | --- | --- |
> | 正则：日期格式、邮箱、URL | "这个数字是真实的温度" |
> | JSON Schema：字段名 / 类型 / 枚举 / 必填 | "这段代码能跑" |
> | CFG/EBNF：编程语言语法、AST | "这段话是不是事实" |

**所以约束解码保证的是"输出属于某个形式语言"，不是"内容正确"。**
这也解释了 §3 里为什么约束后得到的是 `1889-18-19` ——
它满足了 `\d{2}`，但"18 月"从来不是约束要管的事。

#### 级别 3：把"允许的字符"接到模型的"允许的 token"上

级别 1/2 说的都是**字符**，模型输出的是**token**（一个 token 可能含多个字符，
也可能是半个多字节 UTF-8）。所以还要一次翻译：

> **这个 token 的所有字符，都能从当前状态合法走完吗？**

这一步**必须预计算 + 按状态缓存**（否则每步重算 152K × 状态数是灾难）。
实测：状态 0~3 只有 10 个 token 合法，状态 4（该 `-`）**只有 1 个**（见下面的表）。

#### 级别 3 的疑问：词表里怎么会有"选择关系"？

问得很好 —— **词表里没有关系，也不可能有。**

Qwen2 的词表就是**两列**，151,646 条，没有任何第三列：

| token_string（原始键） | id | `decode([id])` |
| --- | --- | --- |
| `'Y'` | 56 | `'Y'` |
| `'E'` | 36 | `'E'` |
| `'YES'` | 14004 | `'YES'` |
| `'-'` | 12 | `'-'` |
| `'Ġthe'` | 279 | `' the'` |

**`'Y'` 后面该跟 `'E'` 这条信息，在词表里完全不存在。** 它在**你的 FSM 代码**里：

```
Qwen2 提供的（扁平字典）        你自己写的（规则）           你把两者【连接】起来
──────────────────────         ──────────────────          ────────────────────────
vocab = {'Y': 56,              TRANS = {1: {'E': 2}}        mask = {}
         'E': 36,                                            for tok_id in vocab.values():
         'YES': 14004, ...}      ← 关系只在这里                 if can_consume(state, decode([tok_id])):
 ↑ 纯字符串表                                                       mask[state].add(tok_id)
   没有任何关系
```

**所以级别 3 的本质是一次"离线扫描 + 求交集"**：把 151,646 个 token 逐个喂给 FSM 试，
活下来的记进 `mask[state]`。**这是一次 join，不是词表自带的结构。**

##### 实测：这个 join 到底有多"狠"

状态 4（该输出 `-`）时：

| | 数量 |
| --- | --- |
| 词表里**含 `-` 的 token** | **2,133** |
| 其中**从状态 4 走完仍合法**的 | **1**（就是 `-` 本身） |

判决细节（真实词表数据）：

| 字符串 | FSM 从状态 4 走完后 | 判决 |
| --- | --- | --- |
| `-` | 落在状态 5 | ✅ 合法 |
| `-K` | 无转移（状态 5 只收数字） | ❌ 拒绝 |
| `-,` | 无转移 | ❌ 拒绝 |
| `}-` | 无转移（状态 4 只收 `-`） | ❌ 拒绝 |

##### 🔍 一个由此暴露的深层事实

**"允许多少 token"同时取决于 grammar 和 tokenizer 的 merge 规则。**

Qwen2 的词表里**没有** `-8` / `-1` 这种"连字符+数字"的合并 token，
所以状态 4 只剩 `-` 一个。**如果**词表里有 `-8`，那么：

```
从状态 4 走 '-8'：'-' → 状态 5，'8' → 状态 6  ✅ 合法（一次跨 2 个字符）
```

→ mask 会更"宽"，模型一次可以吐 2 个字符。

所以：

- **同一个 grammar，换一个 tokenizer，mask 的形态会变**（允许多少 token、每个 token 跨几个字符）；
- 这也是"约束解码的性能"和 **tokenizer 的选择**耦合在一起的原因；
- 反过来，这也解释了为什么真实库要把 mask **按状态缓存**：
  这个扫描是 `151,646 × 状态数`，每步重算是不可能接受的，必须**生成前算一次**。

> 一句话：**词表提供"有哪些积木"，FSM 提供"哪些能拼"，你的扫描代码把两者拼起来变成掩码。**

## 3. 实测：同一个模型、同一个 prompt，只差一个 mask

```
未约束（普通 greedy）      : ' 1889. It is the tallest building in the world'
    匹配 \d{4}-\d{2}-\d{2}?  False

已约束（mask 非法 token）  : '1889-18-19'
    匹配 \d{4}-\d{2}-\d{2}?  True

逐步过程（状态 / 该步合法 token 数 / 选出）：
  状态  0   合法      10/151,646   选了 '1'
  状态  1   合法      10/151,646   选了 '8'
  状态  2   合法      10/151,646   选了 '8'
  状态  3   合法      10/151,646   选了 '9'
  状态  4   合法       1/151,646   选了 '-'      ← 这里只有 1 个 token 合法
  状态  5   合法      10/151,646   选了 '1'
  状态  6   合法      10/151,646   选了 '8'
  状态  7   合法       1/151,646   选了 '-'
  状态  8   合法      10/151,646   选了 '1'
  状态  9   合法      10/151,646   选了 '9'
```

**看第 5 行**：模型本来在 `1889` 后面接着想输出 `.`（写散文），
但状态 4 只允许 `-` —— 所以它**只能**输出 `-`。这就是"约束"的全部魔法。

### ⚠️ 一个极重要的限制

注意约束后的输出是 **`1889-18-19`** —— 格式完全合法，**但 18 月 19 日并不存在**。

> **约束只保证【语法】，不保证【语义】。** 这是它最常见的误用。
> 同理，JSON schema 能保证"字段名合法、类型正确"，**不能保证"内容是真的"**。

## 4. 逐条回答你的疑问

### Q1："引擎不可能预先知道每个用户的规则"

**对，所以引擎不预先知道 —— 规则是请求参数。**

引擎实现的是**通用机制**（状态机 + 掩码），规则由调用方在**每次请求**里带进来：

| 层 | 拥有什么 | 谁写 |
| --- | --- | --- |
| **引擎** | 机制：FSM 执行器、token 掩码预计算与缓存、`logits[mask] = -inf` | 引擎开发者（一次） |
| **请求** | 规则：JSON Schema / 正则 / EBNF / 枚举 | **调用方（每次请求）** |

生产 API 里的典型形态：

| 形态 | 例子 |
| --- | --- |
| OpenAI 风格结构化输出 | `response_format: {"type": "json_schema", "json_schema": {...}}` |
| 工具 / 函数调用 | `tools: [...]` + `tool_choice`（本质就是"输出必须符合这个 schema"） |
| vLLM 的采样参数 | `guided_json` / `guided_regex` / `guided_choice` / `guided_grammar` |
| vLLM 的后端选择 | `--guided-decoding-backend`（outlines / xgrammar / guidance / lm-format-enforcer） |

**所以"面对不同用户"完全没问题**：schema 是请求体的一部分，就像 `max_tokens` 一样。
引擎只负责"拿到一个 schema，就按它约束"。

### Q2："正则怎么能用数学实现？"

**它没有用数学实现 —— 它用编译原理实现。** 分工是这样的：

| 谁 | 干什么 | 用什么 |
| --- | --- | --- |
| Transformer | 给 152K 个候选**打分** | 矩阵乘 / softmax 之前的 logits（神经网络数学） |
| 正则 → 状态机 | 说明"此刻哪些字符合法" | **自动机理论**（Thompson 构造、DFA 最小化） |
| 引擎 | 把"合法字符"翻成"合法 token"，再把非法 logits 设成 -∞ | 查表 + 掩码（`logits[mask] = -inf`） |

**两者只在"掩码"这一点相遇。** 神经网络的数学一点没改 ——
模型照旧算完 152K 个 logits，我们只是**扔掉了其中不合法的那些**。

### Q3："这是 Transformer 里的一个步骤吗？"

**不是。** 它是**采样步骤**的一部分，在 `model.forward()` **之外**。

这就是为什么你在模型代码里"没有印象"——因为它不在那里。
在本仓库里，它对应的是这两行（只有这两处）：

```python
# scheduler.py  _prefill_chunk_blocking（最后一个 chunk 采样首个 token）
first_token_id = int(logits[:, -1, :].argmax(dim=-1).item())

# scheduler.py  _decode_step_single（decode 每步）
next_token_id = int(outputs.logits[:, -1, :].argmax(dim=-1).item())
```

**加约束 = 在这两行的 `argmax` 之前插一个 mask 操作。** 调度器、KV 管理、批处理都不用动。

### 4.3 真实的 FSM 从哪来？—— 编译器产出，不是手写

本文的 demo 为了教学**手写**了状态转移表。**真实系统不手写**，而是用编译器把形式化规格
（JSON Schema / regex / EBNF）**编译**成自动机：

| 库 | 输入 | 关键 API / 描述 |
| --- | --- | --- |
| **xgrammar**（MLC） | JSON Schema / 自由 JSON / regex / **自定义 EBNF** | `Grammar(...)` + **`GrammarCompiler(tokenizer_info)`** → 产出 token 掩码 |
| **llguidance**（Microsoft / guidance） | CFG | 文档原话："computes a **token mask** (allowed next tokens) given a CFG, tokenizer, and token prefix" |
| outlines / lm-format-enforcer | JSON Schema / regex / Pydantic 模型 | 同类思路 |

**注意 `GrammarCompiler(tokenizer_info)` 里的 tokenizer** —— 编译器必须拿到词表，
因为它要把"字符级自动机"翻译成"token 级掩码"（就是本节上面那个 **2,133 → 1** 的扫描）。
这也印证了 §2.5 的结论：**约束机制和词表是绑定的**。

#### 服务商的痕迹：首次编译延迟

**OpenAI 官方文档**（structured outputs）：

> *"the first request with any schema incurs additional latency while the API processes the schema;
> subsequent requests with the same schema do not."*

**这就是"编译 + 缓存"的行为签名**：

| | 发生了什么 | 表现 |
| --- | --- | --- |
| 第一次用某个 schema | 把 schema 编译成自动机 | **额外延迟**（社区实测 10~60 s，非官方数字） |
| 之后同一个 schema | 命中缓存 | 无额外延迟 |

如果只是"在 prompt 里请模型输出 JSON"，**不可能出现这种按 schema 计的首次编译延迟**。

> ⚠️ 服务商内部实现（OpenAI / DeepSeek / …）大多不公开。上面这条是**官方文档里的行为描述**，
> 结合它推断出"编译 + 缓存"是可靠的；但"他们具体用哪个库"**不该乱猜**。

→ **按你装的版本实测，别信文档。**

#### 约束的代价边界（一个真实的妥协）

llguidance 文档里明确记了一条"偏离规范"：**JSON 对象的属性顺序被固定**。

原因很实在：**"任意 key 顺序"要求自动机记住"已经出现过哪些 key"** ——
n 个 key 就有 **2ⁿ** 种已出现集合，状态数直接爆炸。所以它选择固定顺序换状态可控。

> 教训：**不是所有形式化规则都便宜。** 表达能力越强（任意顺序、递归嵌套、跨字段依赖），
> 自动机越大 → 编译越慢、缓存越吃内存。这也是为什么实践里
> **能用浅层 JSON Schema 就别上 EBNF**。

### 4.4 「用户在 prompt 里写的规则」能被保证吗？—— **不能**

这是最容易误解的一点：

| 规则写在哪 | 引擎能看见吗 | 有保证吗 |
| --- | --- | --- |
| **prompt 里的自然语言**（"请输出 JSON"） | ❌ 那只是 token 序列 | ❌ **只是倾向**，靠模型"听话" |
| **请求参数里的结构化规格**（JSON Schema / regex / grammar） | ✅ 能读到、能编译 | ✅ **硬保证** |

**引擎不会去"读 prompt、理解意图"。** 它只处理**形式化的请求参数**：

| 形态 | 例子 |
| --- | --- |
| OpenAI 风格结构化输出 | `response_format={"type": "json_schema", "json_schema": {...}}` |
| 工具 / 函数调用 | `tools=[...]` + `tool_choice` |
| vLLM 采样参数 | `guided_json` / `guided_regex` / `guided_choice` / `guided_grammar` |

所以：

> **"帮我输出 JSON"写在 prompt 里 ≠ 保证；写在 `response_format` 里 ＝ 保证。**

**那如果产品的规则天生是自然语言怎么办？**（比如"输出必须含日期、金额、币种"）

要保证的话，只能**先把它转成 schema**，再拿 schema 去约束生成：

```
自然语言需求 ──(应用层：让模型生成 schema / 或人工写)──► JSON Schema ──► 约束解码 ──► 有保证的输出
     ↑ 这一步不可省                                                  ↑ 只有这一步有硬保证
```

**这是应用层的活，不是推理引擎的。** 引擎只负责"给我一个 schema，我就按它约束"。

> 顺带：即使规则是结构化的，**保证也只覆盖"形式语言能表达的东西"**（§2.5 的能力上限表）——
> JSON Schema 能保证"字段名 / 类型 / 枚举对"，**不能**保证"这个数字是真实温度"。

## 5. 和 `stop` 序列的区别（容易混）

| | `stop` 序列 | 约束解码 |
| --- | --- | --- |
| 管什么 | **什么时候停** | **允许输出什么** |
| 机制 | 生成后做字符串匹配，命中就停 | 生成前 mask 掉非法候选 |
| 保证 | 输出**不会包含**某个片段 | 输出**一定符合**某个语法 |
| 本仓库 | ❌ 未实现（F27） | ❌ 未实现 |

两者互补：`stop` 是"到此为止"，约束是"只能这么走"。
多轮对话/Agent 场景两个都需要（`stop` 防它自己扮演用户，约束保证工具调用可解析）。

## 6. 为什么要关心它（尤其做 Codex 这类产品）

| 场景 | 没有约束 | 有约束 |
| --- | --- | --- |
| 工具 / 函数调用 | 输出可能不是合法 JSON → **事后校验 + 重试**（多花几百 ms 和 token） | **结构上保证可解析** |
| 结构化抽取 | 字段缺失、类型错、多个逗号 | schema 保证字段和类型 |
| 分类 / 路由 | 模型可能输出解释性文字 | `guided_choice` 强制从枚举里选 |
| 代码生成（AST 级） | 语法错误要重试 | grammar 保证可解析 |

**成本**：每步一次掩码（缓存后 ~µs），几乎可忽略；代价主要是**实现复杂度**
（字节级 FSM + 掩码缓存）。

---

## 7. 一句话总结

> **约束解码不在神经网络里，也不改变神经网络的数学。**
> 它是"**给正则写一个状态机，再用状态机把每一步不合法的 token 的分数改成 -∞**"。
> 规则由请求带来，机制由引擎实现 —— 两者在 `logits[mask] = -inf` 这一行相遇。
>
> 它保证**语法**，不保证**语义**。
